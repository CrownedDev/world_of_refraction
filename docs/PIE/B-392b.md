# PIE — B-392b: a co-op guest's guard and parry colour priority reach the host

**Branch:** `fix/B-392b-guest-guard-sync` (merged into `dev`).
**Already proven by tests:** `WoR.Defense.TwoGuards` (co-op): on the host, the guest's own `ServerSetGuard` / `ServerSetParryPriority` change its fighter's guard (and montage) and priority; another player's calls are refused; a fighter with no member id belongs to the player who claims its character; a null fighter is refused without a crash. Not provable headless: the real client-to-host send (needs two machines).
**Setup:** 2-player PIE, **Run Under One Process off**, Play As Listen Server. The guest joins with a weapon user (Generic). For a visible difference, the weapon has a `ParryMontage` and the character's Cosmetics a `BlockMontage` (as in PIE B-392).

| # | Do this | You should see | Result |
|---|---|---|---|
| 1 | Start a fight; on the **host**, `wor.Guard.Print` | The guest's character: `guard Weapon` | [ ] |
| 2 | On the **guest's** window, `wor.Guard.Set Unarmed <guest character name part>` | The guest's log: `guard set to Unarmed (B-392)`. No `[Guard] ... refused` warning in the host's log | [ ] |
| 3 | On the **host**, `wor.Guard.Print` | The guest's character now `guard Unarmed` | [ ] |
| 4 | Let an enemy attack the guest's character; guard it from the guest's window | Both windows show the character's `BlockMontage` (the unarmed guard), not the weapon's | [ ] |
| 5 | On the guest, `wor.Guard.SetParryPriority Magic` (for its character), then land a parry | The host's log: `parry colour priority set to Magic (B-393)` for the guest's character; the parry effect is coloured by the character's own magic, on both screens | [ ] |
| 6 | On the guest, try `wor.Guard.Set Unarmed <host character name part>` | Refused on the host: its log warns `not their fighter`, and the host character's guard is unchanged | [ ] |
