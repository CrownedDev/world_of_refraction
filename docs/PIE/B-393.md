# PIE — B-393: parry landing VFX (spark, parry effect, element colour)

**Branch:** `feature/B-393-parry-vfx` (the cloud's `feature/B-393-parry-vfx-cloud` on dev, after B-392; built on the desktop 2026-11-12; merged into `dev`). **Save v33:** loading an older save (B-392's v32 included) wipes it with a warning (D-060, D-138).
**Already proven by tests (once built):** `WoR.Presentation.ParryVisuals`: a weapon with no element sparks only; unarmed with no element shows nothing; a weapon's crystal tints the weapon guard's effect on top of the spark; the loadout priority picks between adapter and weapon (and falls back when the first has none); an unarmed guard ignores the put-away weapon's crystal; Generic gives no colour; a Perfect Guard drops the spark but keeps the effect; a Refractor's circle takes its source element; the priority setting lives on the loadout (default Weapon).
**Setup:** a fight with a Generic or Resonator holding a weapon with a crystal (e.g. Fire), and a Refractor with no weapon. On each one's Cosmetics data asset, set `GuardSparkVFX` (any spark), `WeaponGuardParryEffectVFX` and `UnarmedGuardParryEffectVFX` (e.g. `NS_Magic_Circle1_*`, AssetAudit; a system exposing the `CoreColor` user colour shows the tint). Turn on `wor.ImpactVFX.Log 1`.

**Known:** with no parry-effect cosmetic authored, the only visible change is that the unarmed guard no longer sparks (check 5). The tint is written to `CoreColor` and `EdgeColor`; a Niagara system without those user parameters plays untinted. A weapon has no element field of its own today: its crystal is its element (Q-393).

**Known (desktop review):** a co-op guest's parry priority stays on its own machine (the host picks the visual), as the guard (Q-392, Q-393). **Known (review):** "unarmed" is any weaponless pawn (B-392's guard), enemies included: a monster whose cosmetics set a guard spark stops sparking on a Guard (D-170: unarmed has nothing by default). `ImpactVisuals::Choose`'s Guard branch is no longer used by play (kept until PIE; the sweep removes it). The two `[PartySession]` guard logs use `LogTemp` like the rest of that file.
